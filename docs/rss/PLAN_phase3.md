# Phase 3: AI分類 + 要約

## 目標

Phase 2で取得した記事本文をLLMに渡し、カテゴリ分類と要約を生成する。

**完了条件**:
- 全記事がいずれかのカテゴリ（`dev_ai` / `industry` / `not_ai`）に分類される
- 全記事の要約テキストが生成される
- API制限エラー時にリトライして処理が継続できる
- 本文取得失敗の記事もタイトル + RSS概要で代替処理できる

---

## 追加するファイル

```
src/
└── classifier.py   ← 新規追加
```

`main.py` と `config.py` も更新する。

## LiteLLM について

**LiteLLM** を使うことで、モデルの切り替えをコード変更なしに実現する。

- Gemini / OpenAI / Claude など100以上のモデルに対応
- `config.py` のモデル名を変えるだけで切り替えられる
- インターフェースはどのプロバイダーでも同じなので `classifier.py` 本体は変更不要

## 各ファイルの役割と留意点

### `src/config.py`（更新）

**追加する設定値**:
- 使用するモデル名（例: `gemini/gemini-2.5-flash`）
- 分類時のTemperature（`0.1`）
- 要約時のTemperature（`0.3`）
- ~~本文の最大文字数~~ → 全文をそのまま渡す（切り詰めない）

モデルを変えたいときはここのモデル名だけ書き換えればよい。

**LiteLLMのモデル名の書式**:

| プロバイダー | モデル名の例 |
|---|---|
| Gemini | `gemini/gemini-2.5-flash` |
| OpenAI | `gpt-4o` |
| Claude | `claude-3-5-sonnet-20241022` |

### `src/classifier.py`

**役割**: LiteLLM を通じてLLMを呼び出し、記事の分類と要約を行うモジュール。

---

#### Step 1: AI判定 + カテゴリ分類

**処理内容**:

1. **入力の準備**
   - 複数記事をまとめてバッチ処理する（5〜10件/リクエスト）
   - 本文が `None`（取得失敗）の記事はタイトル + RSS概要を代替入力として使う
   - 本文は全文をそのまま渡す（切り詰めない。TPM制限超過時は429リトライで対応）

2. **LLMへのAPIリクエスト**
   - ライブラリ: `litellm`
   - モデル: `config.py` の設定値を参照（デフォルト: `gemini/gemini-2.5-flash`）
   - 複数記事のタイトルと本文をまとめて1リクエストで送り、JSON形式で返答させる
   - Temperature: `0.1`（分類のブレを抑えるため低めに設定）

3. **レスポンスのパース**
   - レスポンスから JSON を抽出してパースする
   - レスポンスが期待通りの形式でない場合はその記事を `not_ai` として扱い、ログに残す

**分類カテゴリ**:
- `dev_ai`: 開発に活かせるAIツール・API・実装テクニック・プロンプト手法
- `industry`: AI業界の動向・新モデル発表・研究論文・規制動向
- `not_ai`: AI無関係だが技術的に興味深い記事

**プロンプト（ドラフト）**:

```
あなたは技術記事の分類アシスタントです。
以下の記事リストを読み、各記事を次の3カテゴリのいずれかに分類してください。

カテゴリ:
- dev_ai: 開発に活かせるAIツール・API・実装テクニック・プロンプト手法・AIを使った開発事例
- industry: AI業界の動向・新モデル発表・研究論文・規制動向・企業のAI戦略
- not_ai: AI無関係の技術記事（Web開発、インフラ、言語機能、キャリアなど）

判定基準:
- 記事の主題がAIに関連しているかで判断する
- AIを「使う」記事（プロンプト設計、API活用など）は dev_ai
- AIについて「報じる」記事（新モデル、業界動向など）は industry
- AIに少し触れるだけで主題が別のものは not_ai

以下のJSON形式で返答してください（JSON以外のテキストは不要です）:
[
  {"url": "記事URL", "category": "カテゴリ名"},
  ...
]

--- 記事リスト ---
{articles}
```

**留意点**:
- LLMのレスポンスはMarkdownのコードブロック（` ```json ``` `）で囲まれることがある。パース前にコードブロックを取り除く処理を入れる
- バッチサイズが大きすぎるとトークン制限に引っかかるリスクがある。1リクエストで渡す記事数は10件以下にする

---

#### Step 2: 要約生成

**処理内容**:

1. **1件ずつリクエスト**
   - 分類とは異なり、要約は記事1件ずつ個別にリクエストする
   - バッチにすると要約の質が下がるため

2. **入力の準備**
   - 本文が `None` の記事はタイトル + RSS概要を代替入力として使う（分類と同様）
   - 本文は全文をそのまま渡す（切り詰めない。要約精度を優先し、TPM制限超過時は429リトライで対応）

3. **LLMへのAPIリクエスト**
   - モデル: `config.py` の設定値を参照
   - Temperature: `0.3`（分類より少し高めにして自然な文章を生成）
   - 要約は2〜3行、最大400文字になるよう指示する
   - 日本語で返答させることをプロンプトに明示する（英語記事が混入しても日本語で要約させる）

**プロンプト（ドラフト）**:

```
以下の技術記事を日本語で要約してください。

要件:
- 2〜3行、最大400文字以内
- 記事の核心（何を解決するか、何が新しいか、何が学べるか）を伝える
- 専門用語はそのまま使ってよい
- 要約のみを返答し、前置きや補足は不要

--- 記事 ---
タイトル: {title}
本文:
{content}
```

---

#### API制限・エラー対応

**レート制限（429エラー）**:
- 最大3回リトライする
- リトライ間隔: 1回目 → 10秒、2回目 → 30秒、3回目 → 60秒（指数バックオフ）
- 3回試みても失敗した場合はその記事をスキップしてログに記録する

**その他のAPIエラー**:
- 5xx系エラーは同じくリトライ対象とする
- 4xx系エラー（429以外）はリトライせずスキップする

**リクエスト間隔**:
- 各リクエスト後に6秒スリープして RPM制限（Gemini無料枠: 10 RPM）を超えないようにする

---

#### 無料枠の範囲確認（Gemini使用時）

- Gemini 2.5 Flash 無料枠: 10 RPM / 250 RPD
- 想定リクエスト数: 分類3回（30件を10件/バッチ）+ 要約30回 = **最大33回/日**
- 250 RPD の上限に対して十分余裕がある

## テスト実行

### 手順

1. `.env` に使用するプロバイダーのAPIキーを設定する
2. `config.py` のモデル名が意図したものになっているか確認する
3. `uv add litellm` でパッケージを追加
4. `uv run python src/main.py` を実行する

### 期待される結果

- 各記事にカテゴリ（`dev_ai` / `industry` / `not_ai`）が付与される
- 各記事に日本語の要約テキストが生成される
- コンソールにカテゴリ・要約が表示される
- APIエラーが出ても処理が最後まで完走する

### 処理時間の目安

Phase 2（スクレイピング）の時間に加えて、API呼び出しの時間が追加される。

- 記事30件の場合: Phase 2（約150秒）+ Phase 3（約300秒）= **約7.5分**
